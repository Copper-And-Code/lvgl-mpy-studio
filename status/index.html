    Status: what is verified, and how¶

    Version 0.6.0 is tagged in the repository. No release with packages has been published. This page separates what has been checked from what has only been written.

    Read this first¶

    The project was built broad on purpose: features expected to be useful were included from the start, so that the design would not need to be reopened later. The automated tests are many. Human testing is scarce: few people have used the IDE, and much of what is listed below has never been tried by a person on a real task. Expect rough edges, and treat every "not tried" below as an open question, not as a formality.

    How each area was checked¶

    • Tests: covered by the automated suite, more than 1250 tests.
    • Self-test: exercised in the real IDE window by lvgl-mpy-studio selftest.
    • Board: tried on real hardware, with the board named.
    • Not tried: written and tested by machine only, or not at all.

    Known defects and open points¶

    • Windows. The portable package of 0.4 did not start on a real Windows: it bundled a copy of ICU that hid the system's. The package of 0.6.0 is built without it and starts on Windows 11. The self-test run there passed 76 steps of 78. The step that failed was a mistake of the self-test, which compared a path written with \ with the same path written with /; the step after it was skipped. The run also showed a real defect: when the program ended while a measurement was running, a simulator process stayed alive and its temporary folder could not be removed. Both are corrected, and the author ran the corrected package on Windows 11 without that error. Tests under Wine had shown neither. A third defect, reported by the author, is corrected and not yet seen on Windows: started from the program file, a console window flashed four times at almost every operation.
    • The IDE does not know the pins of a board. A block takes the pin the user types, a number or a name such as PA5, and nothing warns when it is one the display or the memory already uses.
    • The RAM budget shown in the status bar is measured in the 64-bit simulator and is an overestimate for 32-bit boards.
    • Renaming a Python module does not rewrite the code that imports it; the IDE warns.
    • Reference images that hold a changing value fail when the generator changes: the EIM-01 example shows the free memory on a page, and its image had to be regenerated for 0.6.
    • Continuous integration covers tests, not packages. Since the repository became public, each push runs the whole suite and the self-test on Linux, and on Windows the tests of the core, of the runtime and of the IDE, and the self-test. On the Linux machine 72 tests are skipped, because they need what is not built there: the launchers of single-file games, the WebAssembly runtime, Wine, a browser. Packages are built and checked by hand.
    • An upload sends every file again, also those that did not change: a project with fonts takes tens of seconds on a slow link each time.

    What is not there¶

    • The pages that Help → Online Documentation opens: they will be published when the repository becomes public; until then the link leads nowhere.
    • C on boards: only MicroPython is uploaded. The C export is source code for another project.
    • An online catalogue of blocks, and blocks that depend on other blocks.
    • Extensions that run inside the IDE: blocks are data and MicroPython code, nothing more.
    • Blocks for PWM, ADC, I2C, SPI and UART: planned in the plan, not written.
    • A debugger. Errors are reported with file and line; there are no breakpoints.
    • macOS.

    How to check for yourself¶

    .venv/bin/python -m pytest -q        # the whole suite, about ten minutes
.venv/bin/lvgl-mpy-studio selftest   # the IDE uses itself, about twenty seconds

    The self-test writes report.txt with one line for each step. A step that fails is a defect worth reporting.
